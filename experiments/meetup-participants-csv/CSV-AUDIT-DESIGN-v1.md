## 目的

ADMINが**CSV出力権限を明示付与したCAだけ**、自分に割り当てられたCommunityのMeetupをCSVに出力できるようにする。用途を簡潔に申告し、後からADMINが「実行者・対象・目的・日時・成否」を確認できるようにする。権限のないCAにはCSVボタン自体を表示しない。

- 事前承認制ではない。目的は申告必須。**履歴の記録に失敗したらCSV出力禁止（fail closed）。**
- 申告するだけで取得が許可されるのではない。**独立したサーバー側の所属Community/ADMIN権限検査が必須**。
- 300人は将来のCA総数であり、同時アクセス数ではない。初期版に分散ロック、共有待ち行列、過剰な負荷機構を増やさない。

## 1. CA画面：確認ダイアログ

My CommunityのMeetup履歴の既存白パネル・lime配色を維持。既存の詳細表示ボタンとCSVボタンは独立。

1. 「CSV」を押す: **確認ダイアログのみ表示**。この時点で参加者明細の取得・CSV生成・持ち出しログ作成は行わない。
2. 対象Meetup名/開催日時/Community名を表示。
3. 利用目的は**短い一言から必ず選択**する:
   - `mini_game`: ミニゲーム利用
   - `attendance`: 出欠確認と照合のため
   - `event_operations`: イベント運営
   - `other`: その他
4. 直下に**補足情報**（0〜200文字）を置く。通常は任意。**「その他」は空欄不可**。参加者のアカウント名など不必要な情報を入力させない。
5. 「申告した目的以外に使わない／第三者に無断共有しない／不要になれば適切に削除する」を確認するチェックを必須とする。同意のバージョンをサーバー側で管理する。
6. 「生成してダウンロード」押下時だけリクエスト開始。キャンセル/Escは無処理。
7. 取得中は同じボタンを無効化。429・時間切れ・ページ不完全・権限拒否・監査ログ記録失敗のいずれでも **不完全なCSVを渡さない**。エラー本文やアカウント名を画面に流さない。

**禁止したい使い方の例**: 無断の公開配布、SNS掲載、無関係な勧誘、販売・目的外の名簿転用。「目的申告済み」はこれらを許可しない。

## 2. 権限契約

- 実行者のIDはサーバーが検証済みのログインセッションから導出。リクエストで任意のCA/他人のIDを指定させない。
- 対象MeetupはDBの `meetups.id` から取得し、`meetups.community_id` と確実に対応付ける。クライアント指定のCommunity名/IDを権限の根拠にしない。
- **通常CAは追加権限 `CSV_EXPORT` と `community_memberships` による該当Communityの本人割当の両方が必要**。1st/2nd区分やMeetup主催者かどうかでは決めない。初期状態は権限なし。承認待ちユーザーへの付与は禁止。
- ADMINは既存ロールとして権限付与・解除と監査閲覧を行う。CSV出力自体も既存の管理者全権限方針に基づく例外として扱う想定。ただしサーバー側で本人のADMINロールを検証する。
- 既存RLSはMeetup一覧の閲覧制御に使われているが、**CSV名簿の持ち出し権限は別途サーバーで検証**する。リストを見られるだけで全件取得を許可しない。
- 参加者ユーザー名を含むデータの取得は必要最小限・そのリクエスト内のメモリで処理。参加者ID/username/GraphQLレスポンスをDB、監査ログ、運用ログ、Storageに保存しない。

## 2A. CSV専用権限の管理画面（2026-10-16 PO追加指示）

- **全CAには表示しない。権限OFFが初期値**。権限情報の取得失敗・未確定時もCSVボタンは表示しない。
- ADMIN「**👥 CAアカウント**」(`src/app/admin/accounts/page.tsx`) に、既存の「S」権限とは独立した **「CSV権限」ON/OFF** を並べる。新しい管理メニューを増やさない。
- 権限の付与/解除はアカウント単位で管理（候補コード `CSV_EXPORT`）。権限があってもMeetupの所属Communityを横断して取得できない。
- `pending`のアカウントには権限付与不可。ロールをpendingへ戻したときは権限を無効化する（保存状態とサーバー権限判定の両方で安全側）。
- 付与・解除は **ADMINによる認証済みサーバー操作**。UIのON/OFFやブラウザの`hasPermission`だけでアクセス許可を判定しない。解除後のリクエストは即時拒否する。
- 権限更新の失敗はUI上で成功と表示しない。必要に応じ、付与・解除の操作者と日時も監査できる設計にする（保存手段は要承認）。
- 本番実装に想定される依存先（**すべて未変更・事前GOが必要**）:
  - `src/app/admin/accounts/page.tsx`: 既存Sとは別のCSV権限ボタン
  - `src/lib/use-auth-profile.ts`: 既存の`user_permissions`参照と`hasPermission`の利用可能性を検証。認証ロジック自体は変更を避ける
  - `supabase/functions/admin-manage/index.ts`: 現行`set_permission`は`S`しか受け付けない。新コードを追加する場合は高リスク領域としてSTOP
  - `user_permissions`の権限コード制約/RLS/運用設定: `CSV_EXPORT`が既存テーブルで許可されるか未証明。DBスキーマ/Policy変更の可能性は要調査
  - `src/app/community/[id]/page.tsx`: 許可されたCAの行だけCSVボタンをレンダリング
  - 新規独立のサーバー側CSV出力/監査API: **アクセス権限と対象Communityの照合を必ず再実行**

**安全な試作（本番未接続）**:

## 3. 監査ログの最小項目（設計案、未承認）

専用監査記録（例 `csv_export_audit`）を **DB拡張候補** として設計する。具体的SQL名やカラム型は別Phaseの解析後に確定。

| 論理項目 | 内容・保存方針 |
|---|---|
| audit_id | 内部監査レコード識別子 |
| actor_user_id | サーバー側ログイン検証済みアカウント識別子 |
| community_id | サーバー側で確定した対象Community |
| meetup_id | サーバー側で確定したMeetup内部ID |
| requested_at | サーバー時計（UTC保存、日本時間表示） |
| purpose_category | 上記4分類の1つ |
| purpose_detail | 補足情報（通常任意、「その他」では必須、最大200文字）。記入された場合は監査対象 |
| acknowledgement_version | 同意文面の版。チェック有無はサーバー側でも検証 |
| export_state | `requested`, `rejected`, `generation_failed`, `handoff_started` など |
| exported_row_count | CSVを組み立てた件数。未生成はnull |
| failure_code | 個人情報を含まない制御用エラー区分。失敗時のみ |
| updated_at | 状態遷移更新日時 |

- **保存しない**: 参加者のusername、参加者のuserId一覧、CSV内容/ダウンロードURL、トークン、GraphQL生応答、秘密設定、IPアドレスなどの不要な識別情報。
- 実行したCAには本人の申告履歴を表示可能。全CAのログはADMINだけが参照可能。CA自身には更新・削除を認めない。いずれもサーバー側権限で実施。
- 監査目的を超えた保持をしない。保持期間（提案: 12か月）は**未決定**とし、運営とプライバシー要件を確認後POが確定する。削除・退任時の記録維持も別途定義。
- 監査記録には利用目的の文章を含むため、**監査ログそのものも保護対象**。可能な限り記録の書換えを防ぐ。監査レコードとDB操作権限について個別設計。

## 4. サーバー処理順序（実装未着手）

1. 本人の明示的な最終確認によるリクエストを受信する。
2. 認証、**`CSV_EXPORT` 追加権限（通常CA）**、目的カテゴリ/補足情報/同意バージョンをサーバーで検証。既存のS権限はCSV権限の代わりにしない。
3. `meetups.id` を用いて所属Communityと本人割当をサーバーで検証する。通常CAには`CSV_EXPORT`の現在値も再確認する。拒否・解除済みなら名簿データ取得なし。
4. サーバーで **監査開始記録** をDBに書く。記録失敗なら名簿取得を行わずSTOP。
5. Campfire利用許可・GraphQLレスポンス完全性が別ゲートで確認できた場合だけ参加者情報を取得。取得をページ数/時間/対象イベント1件に限定。
6. CSV完成後に **件数と結果状態** を監査記録へ確定する。監査結果が書き込めなければCSVを送信しない。
7. 成功の場合のみHTTPレスポンスとしてCSVを返す。ステータスは `handoff_started` 相当を用い、「ユーザー端末に保存完了」は主張しない。
8. 失敗時は監査側に失敗区分を残して名簿を返さない。エラー時の失敗記録自体が書き込めない場合は安全側へ停止、運用警告の設計を別途検討。

**注意**: 端末へ物理的に保存されたかまでサーバーから証明できない。「出力レスポンス開始までのサーバー処理履歴」として監査する。
