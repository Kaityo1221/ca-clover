## 1. 会長の最大の理想

> 外出先からスマホひとつで、ChatGPTへ日本語で指示し、機能実装 → 隔離試験 → 証跡確認 → 会長の明示的な本番GO → 本番反映・反映後確認まで完結できるようにする。

「スマホだけで完結する開発を標準にし、PCが必要になる作業を例外にする」ことを目指す。単にスマホで進捗を見るだけでなく、既存機能を守りながら修正と再試験を繰り返し、判断に必要な証跡を確認できることが重要である。

ただし、自動化は本番反映の無条件許可を意味しない。AIのPASS報告と人間の本番GOは別の判定である。初期構築、外部OAuth設定、実機操作など、人間やPCが必要な場面は残る可能性がある。現在のChatGPT接続だけで全工程が利用できると約束せず、クラウド実行環境・連携権限・操作可能範囲を将来検証する。

## 2. 開発環境を変える理由と実績の読み方

Vercel Previewへ毎回デプロイする方式への依存を減らし、**ローカル／クラウド実行環境で実装・ビルド・試験を行う方式を主力**にする。外部URL、OAuthリダイレクト、実機での画面確認が必要な場合に、承認された外部確認環境を使う。Vercelの全面廃止や別ホスティングへの即時移行は決めない。

会議で共有されたVercel履歴は、Clover関連**3プロジェクト集計**、日本時間、2026-11-16時点の記録である。

| 対象月 | 成功（READY） | 失敗（ERROR） | キャンセル（CANCELED） | Previewデプロイ記録合計 |
| --- | ---: | ---: | ---: | ---: |
| 2026年9月 | 1 | 0 | 0 | 1 |
| 2026年10月 | 199 | 4 | 19 | 222 |
| 2026年11月（16日時点） | 693 | 21 | 58 | 772 |
| 9〜11月合算 | 893 | 25 | 77 | 995 |

- これは**デプロイ記録の件数**であり、ブラウザでPreviewを実際に閲覧した回数ではない。
- 失敗25件とキャンセル77件は9〜11月の合算であり、11月単月の値ではない。キャンセルをすべてビルド失敗と扱わない。
- 11月は途中集計であり、9・10月の全月値と同条件ではない。
- 利用上限などで拒否され、履歴に残らなかった試行は含まれない可能性がある。これだけで上限到達回数、費用、削減額を断定しない。
- 数値は参照会話と今回の保存指示に基づく会議記録であり、本書作成時にVercel履歴全件を再集計したものではない。

目標はPreview作成回数だけを減らすことではなく、再現可能な試験を増やし、本番を守りながら開発を止めにくくすることである。各サービスの利用枠・費用は別に存在するため、無制限・無料での運用を前提にしない。

## 3. 将来構成と責任の分担

| 構成要素 | 担う役割 | 境界・注意点 |
| --- | --- | --- |
| 会長のスマホ／ChatGPT | 日本語指示、変更・証跡・リスクの確認、GO／STOP | 承認対象と承認者を明確にする |
| GitHub | コード・文書・変更履歴・レビュー | リポジトリ保存だけではアプリやブラウザは実行されない |
| Codex Cloud、GitHub Actions等のクラウド実行環境 | 実装、ビルド、API・DB連携試験、自動ブラウザ試験 | 実際の対応範囲、ネットワーク、永続性、権限を別途検証する |
| ローカル実行環境 | 日常の実装・回帰試験・再現調査 | 外出中のスマホ利用をローカルPCの常時起動に依存させない |
| Neon DBブランチ | 隔離したPostgreSQL・スキーマ・試験データ | ブランチ分離と機密情報保護は別要件 |
| Neon Auth | ブランチ単位の認証状態・認証エンドポイント | アプリの認可・本人照合を自動的に完成させない |
| 外部確認環境／Vercel等 | 必要時の実機・外部OAuth・公開URL確認 | 毎回の修正・試験で作成することを必須にしない |
| 人間の本番承認と反映手順 | 対象を限定した本番GO、反映後確認、障害対応 | 試験用AIに本番反映権限を常時持たせない |

**Neon DB＋Neon Auth自体は、Next.jsコードやブラウザを動かす汎用開発実行環境ではない。** スマホだけでの開発を成立させるには、別途クラウド実行環境が必要である。Neonの他の実行サービスを将来採用するかどうかも、本書では決めない。

NeonでDB・アプリ認証を一元化しても、Google、Discord、Campfire、Vercel OAuth等の外部アカウント、同意、トークン、アクセス権が一つになるわけではない。各サービスとの認証・連携と、Clover内の権限判定を分けて扱う。

## 4. 最優先要求①：Neon DBブランチ＋Neon Authの隔離開発・試験

### 4.1 環境とデータの隔離

| ID | 必須要求 | 受入確認の観点 |
| --- | --- | --- |
| ENV-01 | 作業／機能単位でGitブランチ、クラウド実行環境、Neon DBブランチ、Auth接続先を対応づける | 対応表から対象コミットと試験環境を特定できる |
| ENV-02 | 本番とは別の試験用データ・認証ユーザーを使い、試験の作成・更新・削除を本番へ波及させない | 登録・削除・権限変更が隔離環境だけに留まる |
| ENV-03 | 原則としてスキーマ＋合成テストデータ、または承認済みの匿名化データを用いる | 本人情報、メール、外部ID、トークン等の残存を検査できる |
| ENV-04 | DBだけでなく、認証、ファイル、外部API、通知、Bot、Cron、Webhook等の副作用も隔離する | 試験から実ユーザーへ通知・ロール付与・外部書込みが発生しない |
| ENV-05 | 試験用ブランチの作成・初期化・リセット・終了・削除の手順を再現可能にする | データ初期状態と試験結果を再現できる。証跡は削除前に保全する |
| ENV-06 | DBとAuthの両方のブランチ対応、Cookie・セッション・トークンの境界を検査する | 別環境の認証情報によるアクセスが拒否される |

Neon公式資料では、通常のDBブランチ作成時に認証データ・設定も分岐し、ブランチごとのAuthエンドポイントが用意されると説明されている。一方、元のユーザー・セッション・OAuth設定などが引き継がれ得るため、**ブランチを作っただけで匿名化済みにはならない**。本番からの無加工分岐を既定の開発手順にしない。参照：[Branching authentication](https://neon.com/docs/auth/branching-authentication)。

機密データを含めない選択肢としてスキーマのみのブランチがあるが、対象構成でのAuth初期化・試験ユーザー投入・制約は実移行前に検証する。利用可能性や仕様変更も確認する。参照：[Schema-only branches](https://neon.com/docs/guides/branching-schema-only)。

### 4.2 強制的な本番誤接続防止

注意書きやAIの自己申告だけに頼らず、将来の実行基盤で次を強制する。

- 本番DB、Auth、Storage、外部サービスの本番接続情報を試験実行環境へ渡さない。権限を限定し、本番管理資格情報をAIの通常作業から分離する。
- 起動・試験開始時に、許可されたプロジェクト／ブランチ／DB／Authエンドポイントの組合せを検査する。名称や「test」文字列だけで安全判定しない。
- 接続先が不明、不一致、未設定なら処理を停止する。本番接続先への自動フォールバックを禁止する。
- 本番宛てDB接続・外部書込みを資格情報・権限・通信制御などで拒否する。具体方式は実現可能性を検証して決める。
- 本番接続先の混入、別ブランチのAuth URL、欠落した設定を意図的に与え、接続・処理が止まる負の試験を必須とする。
- 本番サービスへの疎通を行って防御を試すのではなく、隔離環境で拒否動作を証明する。実本番での確認が必要なら別計画・別承認とする。

## 5. 最優先要求②：Google／Discord／CAマスター／Meetup本人照合の安全性

### 5.1 混同してはいけない識別子

| 対象 | 確認するもの | それだけでは証明できないもの |
| --- | --- | --- |
| Googleログイン | 正規の認証手順で確認したGoogleアカウントの識別子 | CA資格、Discord所属、Meetup主催者であること |
| Discord連携 | 正規の認証手順で確認したDiscordユーザーIDと必要な所属／ロール情報 | 表示名の一致によるGoogle・CA・Meetupとの同一人物性 |
| CAマスター照合 | **トレーナー名**を用いるCA情報の照合 | Scopely IDとの同一視、名前一致だけによるアカウント所有証明 |
| Campfire Meetup主催者照合 | **Scopely ID**を用いる主催者情報の照合 | トレーナー名との同一視、入力文字列だけによる所有証明 |
| Clover内アカウント／権限 | 承認された紐づけ規則とサーバー側の認可 | 外部ログイン成功だけによるADMIN昇格 |

トレーナー名とScopely IDは別の情報である。AIは入力欄の意味、取り違え、修正方法を説明できるが、**本人判定、CA承認、アカウント統合、権限付与の決定を行ってはならない**。主催者情報の取得経路・信頼できる照合根拠・人間による確認手順の詳細は今後設計する。Scopely IDの自己申告一致だけで本人確認済みにしない。

### 5.2 認証・紐づけ・認可の要求

- 外部認証情報はサーバー側で検証し、プロバイダーと安定した識別子を組にして扱う。表示名やメールアドレスの一致だけで別アカウントを自動統合しない。
- OAuthの戻り先、state、nonce、PKCE等は採用フローに応じて検証し、改ざん・使い回し・別環境混入を拒否する。必要な設定・対応範囲は各サービスで確認する。
- 連携の追加・解除・再連携は、現在のアカウント所有と対象外部アカウントの確認を必要とする。別利用者の連携を上書きしない。
- CA照合、Discordの所属／ロール確認、Meetup主催者照合、Clover内の権限付与を個別に記録し、どの根拠で認可したか追跡可能にする。
- 照合不一致、重複、曖昧な名前、改名、既存連携済み、権限不足、外部サービス障害では自動承認を停止し、管理者が確認できる保留状態とする。
- 権限は画面の表示制御だけでなくAPI・サーバー側で強制する。必要なDB権限制御も含め、一般ユーザーがADMIN機能や他人のデータへ到達できないことを確認する。
- 認証情報・トークン・Cookie・秘密値を公開GitHub、AIへの通常入力、スクリーンショット、試験ログへ露出させない。

### 5.3 必須の認証・本人照合試験

正常な登録・ログイン・ログアウト・再認証に加え、次を必須とする。

1. トレーナー名／Scopely IDの取り違え、同名・似た名前、改名、未掲載、主催者不一致。
2. GoogleとDiscordが別人、既存連携との競合、重複アカウント、連携解除後の古い状態。
3. 期限切れ・不正なトークン、OAuth戻り先の不一致、別ブランチのセッション、権限剥奪後のアクセス。
4. 一般ユーザーからADMIN APIへの直接呼出し、他ユーザーのIDへの差替え、同時実行による二重登録・二重承認。
5. Discord／Campfire等の障害・タイムアウト・データ不足時に、本人確認や権限付与が安全に停止すること。

模擬OAuth試験のPASSを実際のGoogle／Discord認証のPASSと読み替えない。外部認証・実機試験が未実施なら、証跡と報告に明記する。

## 6. AIの利用範囲と登録エラー支援の例外

- AI機能は**原則ADMIN専用**とする。
- 例外として、ユーザー登録エラー支援は**アカウントにつき初回1回のみ**利用可能とする。
- **2回目の登録エラーでは、そのアカウントの登録エラー支援AIを停止し、管理者向けレポートへ送る。** 自動再試行や画面の再読込みで支援回数を復活させない。
- AIは状況整理と説明補助を行う。本人認定、CA資格の決定、承認・権限付与、認証回避、無承認のデータ修正を行わない。
- 管理者レポートは、必要最小限のエラー分類、時刻、処理状況、追跡ID等で調査できるようにし、秘密値や不要な本人情報を含めない。
- 「アカウント」の確定時点、初回の数え方、登録未完了時の識別、同時発生時の原子的な回数管理、再開／解除権限、保存期間、通知経路、レポート詳細は将来検討とする。未定義の間は実装開始の根拠にしない。

AIモデル、AI Gatewayの採否、トークン量、料金体系、課金連携、利用上限の詳細設計は後回しとする。今回、契約・料金プラン・支払い設定を変更しない。

## 7. スマホからの将来の標準開発サイクル

| 段階 | 期待する動作 | 次へ進む条件 |
| --- | --- | --- |
| 1. 指示と範囲確定 | 会長が日本語で機能・禁止事項を指示。変更可能範囲と成功条件を整理 | 範囲とリスクが明確 |
| 2. 隔離準備 | 専用Gitブランチ、クラウド実行環境、DB・Authブランチを対応づける | 本番誤接続防止と副作用の隔離を確認 |
| 3. 実装と試験 | 機能実装、ビルド、API・DB・認証・権限・画面・回帰試験。失敗時は範囲内で修正・再試験 | 必須試験の証跡が揃う |
| 4. 証跡確認 | スマホで変更点、差分、PASS／FAIL／未実施、画像、リスクを確認 | 不明点と残存リスクが明示される |
| 5. 人間の判定 | 会長が対象を指定して本番GOまたはSTOP | **明示的な本番GOがある場合だけ**反映準備へ |
| 6. 本番反映 | 承認されたコミット・変更・手順だけを限定権限で実行 | 対象差分・設定・承認が一致 |
| 7. 反映後確認 | 主要機能、認証、権限、エラーを確認。問題時は停止・復旧 | 結果と証跡を報告・保全 |

本番GOには、少なくとも対象リポジトリ・コミット／差分、環境、反映範囲、試験結果、残存リスク、復旧方法を対応づけ、承認者・時刻を記録する。承認後にコミットや反映範囲が変わった場合は再レビュー・再承認する。曖昧な相づち、過去の別作業のGO、AIのPASS、応答がないことを本番GOとして扱わない。

AIによる実装と、人間による仕様・UI判断・本番承認の役割分離を維持する。通信断・実行中断後は、どこまで処理されたか証跡から確認して再開し、本番反映を二重実行しない。実現方式は別途検証する。

## 8. 試験証跡・権限・監査の要求

### 8.1 最低限残す証跡

- 実行ID、日時・タイムゾーン、対象Gitコミット、DB／Authブランチの識別子、実行環境、試験データの版。
- 試験項目、期待値、結果、PASS／FAIL／未実施／確認不能の区別、失敗原因と修正・再試験の対応。
- 本番誤接続拒否、認証・認可の拒否、本人照合不一致、外部副作用の隔離を確認した結果。
- 画面のスクリーンショットや操作記録、必要に応じてPC／スマホの表示差、実機確認の有無。
- 変更差分、既存機能への影響、残存リスク、承認と本番反映結果、復旧結果。

証跡はスマホから確認可能にし、詳細ログへの導線を用意する。秘密・個人情報を除去し、機密の証跡は公開リポジトリへ置かない。ログ保存先、アクセス権、保持期間、改変検知・履歴管理の方式を定める。試験用ブランチの削除と証跡の保全を混同しない。

### 8.2 権限と監査

開発AI、試験実行者、管理者、承認者、本番反映者の権限を分ける。試験では最小権限とし、本番反映に必要な権限だけを承認後に限定して使う。誰が、いつ、どの差分を、どの根拠で承認・実行したか追跡できることを必須とする。詳細な権限設計と監査基盤は将来設計する。

## 9. 既存機能・成功済み試験成果・資産の保持

- 既存機能、UI資産、画像・メダル等の素材、登録情報、履歴、設計文書、成功済み試験の手順・結果・証跡を棚卸しし、次世代へ引き継ぐ。
- 過去の成功済み試験を捨てず、対象コミット・データ・環境・前提条件とともに回帰試験へ取り込む。過去PASSだけで新環境のPASSと判定しない。
- 現行と次世代の機能対応表を作り、保持・移行・意図的な廃止・未検証を区別する。欠落をAIの判断だけで削除扱いにしない。
- 公開フロントエンドと非公開バックエンドの境界を維持する。本リポジトリが公開であることを踏まえ、秘密情報、内部実装、私的証跡を文書と一緒に転載しない。
- **次世代ではCampfireの自動巡回機能を廃止する予定**とする。代替のデータ取得・更新・主催者照合の方式は別途設計・承認する。今回、現行本番の巡回・取得・Cron等を停止しない。
- 廃止予定を理由に、現行機能や証跡・バックアップを先に削除しない。旧方式が不要と確認できるまで、退避・復旧可能性を維持する。
